# Incremental Clickstream Sessionizer (DuckDB)

## Problem
Raw clickstream feeds arrive as JSONL batches that contain malformed rows, duplicate
events, and **late-arriving events**. Analysts need correct sessions (30-minute inactivity
gap) and daily metrics, without reprocessing all history on every batch.

## Architecture
```
batch.jsonl -> validate (quarantine bad rows with reason)
            -> dedupe (in-batch + against stored events, by event_id)
            -> INSERT ... ON CONFLICT DO NOTHING into `events`
            -> re-sessionize ONLY users touched by the batch (window functions: lag + running sum)
            -> rebuild `daily_metrics` -> record in `processed_batches`
            -> optional Parquet export partitioned by session_date
```
Everything for a batch runs in one transaction; failure rolls back fully.

Tables: `events`, `quarantine`, `sessions`, `daily_metrics`, `processed_batches`.

## Setup
```
python -m pip install -r requirements.txt
```

## Usage
```
python -m sessionizer.cli run data/sample                 # in-memory demo
python -m sessionizer.cli run data/batches --db out/clicks.duckdb --parquet-dir out/sessions
python -m pytest -q
```
`data/sample/` holds two hand-written batches (the second has a late event that bridges
two sessions of u1) with `expected_after_batch1.csv` / `expected_after_batch2.csv`.
`data/batches/2026-11-01.jsonl` is synthetic (generated by `sessionizer/generate.py`, seed 7)
with 3 injected bad rows and 1 duplicate.

Measured output on the sample: batch 1 -> read 9, loaded 4, duplicates 1, quarantined 4;
batch 2 -> loaded 1, duplicates 1; final daily metrics: 2 sessions, 2 users, avg 1800 s,
conversion 0.5. Synthetic batch: 158 loaded, 3 quarantined, 1 duplicate, 35 sessions.

## Design decisions
- **Re-sessionize per affected user** rather than patching sessions: simple and provably
  correct for late data (merges and splits both handled), cost proportional to touched users.
- **Idempotency** through `processed_batches` plus `event_id` primary key; `force=True`
  reprocesses safely.
- **Gap rule**: a gap strictly greater than the threshold starts a new session (exactly 30 min stays).
- Timestamps with offsets are normalised to naive UTC.
- Ties on `ts` are broken by `event_id` for deterministic ordering.
- Session id = user + start time, so it is stable unless a late event moves the start.

## Limitations
- Per-user history is fully re-read; very heavy users or huge histories would need bounded lookback.
- Sessions are dated by start time; sessions spanning midnight count on the start day.
- Late events that change a session's start also change its `session_id`.
- Single-writer DuckDB; no concurrency control across processes.
- Events with the same `event_id` but different content: the first one wins silently.
- Python `executemany` inserts are fine for demo scale, not for millions of rows (use `read_json` bulk load).
